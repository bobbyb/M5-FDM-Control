# G-code flavours: eufyMake vs OrcaSlicer

How the two slicers that matter for the AnkerMake M5 differ, and what M5 FDM Control
does about it.

Both samples in `src/gcode samples/` are the same model sliced for the same printer:

| | eufyMake (AnkerMake Studio 1.5.26) | OrcaSlicer 2.3.2 |
|---|---|---|
| File | `90 Clippy Blade_0.2mm_AnkerMake PLA+ Basic_M5.gcode` | `90 Clippy Blade_0.2mm_PLA_Anker M5.gcode` |
| Size | 758,589 B / 30,435 lines | 882,947 B / 37,398 lines |
| Producer line | `; generated by AnkerMake Studio 1.5.26 on ... UTC` | `; generated by OrcaSlicer 2.3.2 on ...` |

Everything below was verified against these two files, not inferred from documentation.

---

## 1. Structure

**eufyMake** is a flat file. The producer line is first, then an Anker-specific header
block of `;Key:Value` pairs, then the body, then a PrusaSlicer-style config dump.

**OrcaSlicer** wraps everything in named block markers:

```
; HEADER_BLOCK_START    ... ; HEADER_BLOCK_END
; THUMBNAIL_BLOCK_START ... ; THUMBNAIL_BLOCK_END   (once per thumbnail)
; CONFIG_BLOCK_START    ... ; CONFIG_BLOCK_END
```

eufyMake delimits only its config dump, and with a different marker:
`; ankerslicer_config = begin` / `= end`. Its last line is `;AnkerMake version: V1.5.26`.

> **Parsing trap.** OrcaSlicer's `THUMBNAIL_BLOCK_END` is uppercase and would collide with a
> case-insensitive search for the payload terminator `thumbnail end`. `GcodeInfoScanner`
> matches case-sensitively for exactly this reason.

## 2. Print summary metadata

This is what the app reads before sending a job. **The two files agree on the footer
format** — this is why OrcaSlicer support was cheap.

Both emit, near the end:

```
; filament used [mm] = ...
; filament used [g] = ...
; total filament used [g] = ...
; total filament cost = ...
; estimated printing time (normal mode) = 20m 35s
```

eufyMake **additionally** emits an AnkerMake-style header near the top:

```
;Filament weight: 3.43525g
;Filament used: 1151.78mm
;TIME:1235.4s
```

Note the two disagree slightly on precision — header `3.43525g` vs footer `3.44`. The app
reads the **footer**, because the producer is detected as AnkerStudio.

### Fields only eufyMake provides

```
;MINX: ;MINY: ;MINZ: ;MAXX: ;MAXY: ;MAXZ:     -> object bounding box
; max_print_speed = 250                        -> max speed
;Machine Name:AnkerMake M5
;Filament Name:AnkerMake PLA+ Basic
;Profile Name: / ;Print Mode:
;multi_model: ;support_enable: ;adhesion_type: ;damaged: ;repaired:
```

OrcaSlicer emits **none** of these. Consequences in the app: an OrcaSlicer job shows no
max speed and no bounding box. Both fields simply stay empty; nothing else is affected.

`;Machine Name:` / `;Print Mode:` matter beyond display — `GcodeInfo::GetMachineInfoFromGCode`
uses them to identify the target machine (M5 / M5C / M5 V6) and to decide whether a file is
Anker-branded. **OrcaSlicer files carry no such marker.**

## 3. Thumbnails

| | eufyMake | OrcaSlicer |
|---|---|---|
| Count | 1 | 2 |
| Sizes | 256x256 | 48x48 **and** 300x300 |
| Header form | `thumbnail begin 256x256 3128` | `thumbnail begin 300x300 3136` |
| Encoding | base64 PNG, one `; `-prefixed line each | same |

AnkerMake (the older, non-Studio producer) writes dimensions space-separated instead:
`thumbnail begin 256 256`.

The scanner therefore parses dimensions generically — `WxH` or `W H` — and when a file
carries several, **keeps the largest**. It stops looking once it holds one at least
256x256 (`PREFERRED_THUMBNAIL_AREA`).

> This replaced a hardcoded match on the literal string `thumbnail begin 256x256`. That
> older behaviour silently dropped every non-256 preview: OrcaSlicer's 300x300, and also
> PrusaSlicer files that emit 128x128. Those showed a placeholder image instead.

## 4. Feature annotations (`;TYPE:`)

Both use full role names, but from **different vocabularies**:

| eufyMake (PrusaSlicer lineage) | OrcaSlicer (Bambu lineage) |
|---|---|
| `Perimeter` | `Inner wall` |
| `External perimeter` | `Outer wall` |
| `Overhang perimeter` | `Overhang wall` |
| `Internal infill` | `Sparse infill` |
| `Solid infill` | `Internal solid infill` |
| `Top solid infill` | `Top surface` |
| — | `Bottom surface` |
| `Bridge infill` | `Bridge` / `Internal Bridge` |
| `Gap fill` | — |
| `Skirt/Brim` | `Skirt` |
| `Custom` | `Custom` |

`GCodeProcessor` already understands both vocabularies, so the g-code preview colours
either correctly. This matters only for preview rendering — it is not used when sending a
job.

## 5. Layer markers

| eufyMake | OrcaSlicer |
|---|---|
| `;LAYER:<n>` (113x) | `;LAYER_CHANGE` (113x) then `;Z:` and `;HEIGHT:` |
| `;LAYER_COUNT:` once | `; total layer number:` in the header block |
| `;AFTER_LAYER_CHANGE` | `;BEFORE_LAYER_CHANGE` / `;AFTER_LAYER_CHANGE` |

Both files are 113 layers. eufyMake numbers each layer inline; OrcaSlicer emits an unnumbered
change marker and puts the total in the header. **Anything counting layers by scanning must
handle both.**

## 6. Machine commands

Shared: `G1 G21 G28 G90 G92`, `M83` (relative E — both), `M104/M109/M190`, `M73` progress
(~118 in each), `M204`, `M205`.

| Only eufyMake | Only OrcaSlicer |
|---|---|
| `M107` (fan off) | `M201` (max acceleration) |
| `M84` (disable steppers) | `M203` (max feedrate) |
| `G17` + `G3` (one arc, in start g-code) | `M18` (disable steppers) |
| | `M4899 T3` (Anker v3 jerk / S-curve accel) |

Three things worth knowing:

- **`M4899 T3` is an Anker-specific command** OrcaSlicer emits and eufyMake does not — its
  Anker profile enables v3 jerk and S-curve acceleration explicitly.
- `M84` vs `M18` are the same operation (disable steppers) spelled differently.
- **Fan handling differs sharply.** eufyMake touches the fan three times in the whole file
  (`M107`, one `M106 S255`, `M107`). OrcaSlicer issues `M106` **74 times**, modulating per
  feature, and turns the fan off with `M106 S0` rather than `M107`. Anything keying on
  `M107` to detect fan-off will miss every OrcaSlicer file.

The `G17`/`G3` pair in the eufyMake file is a **single arc in the start sequence** (line 114,
the initial priming move), not arc output through the body — both files are otherwise
entirely `G1` linear moves. Worth knowing only if you write a parser that would choke on an
unexpected `G3`.

Sample start-up temperatures differ only because the profiles differ (eufyMake 230/65,
Orca 220/60) — not a flavour difference.

## What the app does with each

| | eufyMake | OrcaSlicer |
|---|---|---|
| Producer detected | AnkerStudio | OrcaSlicer |
| Print time | 1235 s (`20m 35s`) | 1110 s (`18m 30s`) |
| Filament weight | ` 3.44g` | ` 3.30g` |
| Filament length | ` 1151.78mm` | ` 1107.17mm` |
| Filament cost | ` 0.00` | ` 0.08` |
| Max speed | ` 250` | *(not emitted)* |
| Bounding box | 18.445 / 11.596 / 22.4 | *(not emitted)* |
| Thumbnail | 256x256, 2345 B PNG | 300x300, 2352 B PNG |
| Machine ID from g-code | `AnkerMake M5` | *(not emitted)* |

Values are as returned by `GcodeInfoScanner::Scan`; leading spaces are preserved because the
strings are taken verbatim after the tag, matching the original upstream behaviour.

## Adding another slicer

`GcodeInfoScanner` (`src/slic3r/Utils/GcodeInfoScanner.{hpp,cpp}`) is self-contained — no
libslic3r, no wxWidgets. To add a producer:

1. Add an `EProducer` entry and a signature to the `Producers` table. **Order matters** —
   more specific signatures first, which is why `generated by AnkerMake Studio` precedes the
   bare `AnkerMake`.
2. Add it to the supported-producer check in `Scan()`, or the scan bails out immediately.
3. If it writes the PrusaSlicer-style footer, add it to `uses_slic3r_footer()` and the
   metadata matchers work unchanged. That is all OrcaSlicer needed.

A producer that is recognised but has no grammar stops the scan at once, rather than reading
the whole file to no purpose. An **unrecognised** producer is worse: detection never fires,
so the file is read to the end and nothing is extracted. That was OrcaSlicer's behaviour
before it was added — no print time, no filament figures, placeholder preview.
